Vision and hypotheses: not built, not measured

Where this could go.

Four what-ifs for a memory that keeps its own order. They are ideas, written down so that someone can test them or throw them away.

How to read this page: none of it exists yet, and none of it has been measured. No sentence here is evidence for a claim on any other page. What TRACE has really shown, with its limits, is on Evidence and limits.

Before you read on

TRACE is a research prototype. This page makes no claim about medical, legal or safety-critical use, and TRACE is not fit for any of them. Each what-if ends with what would have to be true first.

What if 1

The right context arrived at the right moment

An assistant forgets everything that is not in front of it. A good memory would not hand it everything. It would put the few right pieces on the desk just as the work needs them.

That is the direction TRACE’s way of searching points in: a memory that sorts itself as it grows, so that for any moment it only has to look at a small part of itself.

What would have to be true first

  • The order must hold as the memory grows. We checked collections of 10,000 to 233,000 passages and found the order at every size, with no trend either way. We have not checked millions.
  • The right pieces must come quickly. Today a TRACE search takes 1.2 seconds on our library, against 88 milliseconds for a plain scan.
  • “Right” must mean useful. On our 50 test searches, ordinary keyword search found the right source more often than TRACE (82% against 52%).
What if 2

The messy documents in your life arranged themselves

Notes, saved web pages, long email threads, PDFs. Nobody files them, and folders never survive real life. What if you gave a memory the documents you choose, and it laid them out with neat connections, by itself, at a size no person could tidy by hand?

You would stop looking for a file name. You would ask, and each answer would point back to the page it came from.

What would have to be true first

  • It must cope with messy text. Our library is English Wikipedia, which is tidy. TRACE has not been run on public benchmarks, and a simple stand-in of ours did very differently on different public sets.
  • New material must join without starting over. That is the design aim. We have no measured curve of a library growing.
  • Private stays private. No service exists for this today. Our public backend is switched off, and nothing here is a promise about handling anyone’s documents.
What if 3

A researcher compared one new case with every earlier case

A researcher meets something new: an odd experiment result, a puzzling failure in a machine, a bug nobody has seen. The question is always the same. What have we seen before that looks like this?

The memory would bring back the nearest earlier cases, and every one would carry a record of where it came from: which document, where in it, and a fingerprint that shows the text has not changed since it was stored.

What would have to be true first

  • “Nearest” must mean “comparable”. We only measured that TRACE keeps what exact search by meaning finds. We did not measure whether what it finds is the right comparison.
  • A record is not a verdict. A matching fingerprint shows the text is the stored one. It does not show the earlier case is relevant, or that its conclusion was right.
  • A person stays responsible. The memory would offer comparisons. The judgement would remain with the researcher.
What if 4: for readers who want depth

Fast retrieval, slow deliberation, and knowledge that moves between them

This section uses technical language. It states two hypotheses and how each could fail. The terms “system 1” and “system 2” come from psychology, where they name fast, automatic judgement and slow, deliberate reasoning. We use them as a design analogy only, and make no claim about how brains work.

H1: two speeds beat one

A fast stage that returns candidates by waking a small part of an index, followed by a slow stage that reads the candidates and their records and reasons over them, may answer correctly more often than the fast stage alone, at a cost we can measure.

  • How to test: the same 50 test searches, plus a larger written set, with and without the slow stage. Score whether the source is in the top ten and whether the final answer is correct by a fixed rubric. Report the extra time and cost per question.
  • It fails if the gain over the fast stage alone is within noise, or if ordinary keyword search plus the same slow stage does as well, which would make the self-organizing part unnecessary.

H2: knowledge moves from the slow mode to the fast one

When the slow stage keeps reaching the same conclusion from the same sources, writing that conclusion back into the memory as a new entry, with the records of its sources, lets the fast stage find it next time. The slow stage would then be called less often for questions we have already worked out. This is inspired by how a practised skill becomes habit, and is nothing more than that: an analogy.

  • How to test: replay a stream of repeated and related questions. Count slow-stage calls per question as written-back entries pile up, and check that correctness holds.
  • It fails if the calls do not fall, or if errors rise because a wrong conclusion, once written back, returns later looking like a confident answer. Every written-back entry would need to carry its source records and be removable.

Status: not built. No slow stage, no write-back and no test of either exists in this repository.
