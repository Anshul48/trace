## 1. Executive Summary & Verification Principles

The Independent Verifier operates strictly outside the implementation lanes. In accordance with `01_INVARIANTS.md` (Invariants 2, 4, 7, 8) and `SESSION_OPERATING_MANUAL.md`:
1. **Never Repair Implementation:** If a candidate fails a verification case, the verifier documents the failure, emits an error receipt, and returns the candidate for implementation repair. The verifier never patches candidate code.
2. **Never Relax Acceptance Criteria:** An attractive retrieval metric or developer convenience never waives an invariant failure, candidate leakage, or unhandled fallback.
3. **Fail-Closed by Construction:** Certification mode must fail closed with an explicit, structured error receipt on any missing data, unpinned source, mock provider, synthetic substitute, flat fallback, stage exception, or TLS failure. It must never produce a certifying-looking score or silent abstention win.
4. **Candidate Invisibility & Prior-Active Preservation:** Candidate derived state (hierarchy, vectors, lexical postings, graph edges, activation priors) must remain completely invisible to ordinary reads. A failed, interrupted, or invalid build must leave the predecessor active release fully readable and intact.
5. **Infrastructure Boundary Enforcement:** In-memory, fake, or SQLite tests verify logical state transitions and contract schemas only. They must never be cited as proof of PostgreSQL durability, Row-Level Security (RLS) enforcement, external-index atomic alias swapping, or production crash recovery.

## 4. Verification Evidence & Error Receipt Standard

Every verification execution must generate:
1. **Verification Report:** Conforming to `templates/VERIFICATION_REPORT_TEMPLATE.md` containing exact environment capture, commit hashes, test commands, state before/after diffs, and promotion recommendation (`accept`, `repair`, `reject`, `defer`).
2. **Error Receipts:** Conforming to `templates/ERROR_RECEIPT.schema.json` with strict schema validation.
3. **Evidence Index Entry:** Conforming to `templates/FOUNDATION_EVIDENCE_INDEX_TEMPLATE.md`.
4. **Digest Bundle:** SHA-256 manifest of all generated test logs, raw queries, database snapshots, and receipts.

## 5. Scope & Claim Boundaries

- **What this plan establishes:** Complete, immutable, frozen negative and lifecycle test definitions for V1a and V1b.
- **What this plan does NOT establish:** It does not certify any runtime implementation, does not waive any pending decision (P-001..P-008), and does not declare any component release-ready.
